# Архитектура проекта: DDD + Clean Architecture

## Структура проекта

```
src/grpc_tutorial/
├── domain/              # 🎯 СЛОЙ ДОМЕНА (бизнес-логика)
│   ├── models/         # Сущности и Value Objects
│   ├── services/       # Доменные сервисы (бизнес-операции)
│   └── repositories/   # Интерфейсы для работы с данными
│
├── application/         # 📋 СЛОЙ ПРИЛОЖЕНИЯ (use cases)
│   └── use_cases/      # Сценарии использования
│
├── infrastructure/      # 🔧 СЛОЙ ИНФРАСТРУКТУРЫ (технические детали)
│   ├── grpc/           # gRPC реализация
│   │   ├── proto/      # Protocol Buffer файлы
│   │   ├── server/     # gRPC сервер
│   │   └── client/     # gRPC клиент
│   └── persistence/    # Хранилище данных (БД, файлы, memory)
│
└── presentation/        # 🎨 СЛОЙ ПРЕДСТАВЛЕНИЯ (API handlers)
    └── grpc_handlers/  # Обработчики gRPC запросов
```

## Объяснение слоев

### 1. Domain Layer (Домен) - САМЫЙ ВАЖНЫЙ
**Что здесь:** Бизнес-логика, правила, сущности

**Пример:**
- `User` - сущность пользователя
- `UserRepository` - интерфейс (НЕ реализация!) для работы с пользователями
- `UserService` - бизнес-операции (например, валидация email)

**Правило:** Этот слой НЕ ЗНАЕТ о gRPC, базах данных, HTTP и т.д.

### 2. Application Layer (Приложение)
**Что здесь:** Use Cases - сценарии использования приложения

**Пример:**
- `CreateUserUseCase` - сценарий создания пользователя
  1. Получить данные
  2. Валидировать
  3. Создать User
  4. Сохранить через Repository
  5. Вернуть результат

**Правило:** Использует Domain, НЕ ЗНАЕТ о деталях инфраструктуры

### 3. Infrastructure Layer (Инфраструктура)
**Что здесь:** Технические детали реализации

**Пример:**
- gRPC сервер и клиент
- Реализация Repository (InMemoryUserRepository, PostgresUserRepository)
- Работа с файлами, внешними API

**Правило:** Реализует интерфейсы из Domain

### 4. Presentation Layer (Представление)
**Что здесь:** Обработчики запросов (адаптеры)

**Пример:**
- `UserGrpcHandler` - принимает gRPC запросы, вызывает Use Cases

**Правило:** Преобразует внешние запросы во внутренние команды

## Поток данных (Data Flow)

```
1. Клиент → gRPC запрос
2. Presentation (UserGrpcHandler) → получает запрос
3. Application (CreateUserUseCase) → выполняет бизнес-логику
4. Domain (User, UserRepository) → работает с сущностями
5. Infrastructure (InMemoryUserRepository) → сохраняет данные
6. ← Ответ идет обратно по цепочке
```

## Преимущества такой архитектуры

✅ **Тестируемость** - каждый слой легко тестировать изолированно
✅ **Независимость от фреймворков** - можно заменить gRPC на REST без изменения бизнес-логики
✅ **Независимость от БД** - можно заменить БД без изменения логики
✅ **Понятность** - каждый слой имеет четкую ответственность
✅ **Масштабируемость** - легко добавлять новые фичи

## Принцип Dependency Rule

```
Domain ← Application ← Infrastructure
   ↑         ↑              ↑
   └─────────┴──────────────┘
           Presentation
```

**Правило:** Зависимости направлены ВНУТРЬ к Domain
- Domain не зависит НИ ОТ ЧЕГО
- Application зависит только от Domain
- Infrastructure зависит от Domain и Application
- Presentation зависит от всех остальных
